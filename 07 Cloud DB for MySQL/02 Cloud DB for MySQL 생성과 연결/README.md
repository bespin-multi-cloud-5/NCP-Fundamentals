# 07 Cloud DB for MySQL / 02 Cloud DB for MySQL 생성과 연결

관리형 데이터베이스를 생성하고 다른 존의 서버에서 접속한다. 생성 화면 두 단계가 무엇을 결정하는지, 생성한 뒤에 무엇을 개방해야 연결되는지 다룬다.

## What you will learn

- 이름이 셋이고 가리키는 대상이 각각 다르다는 점 — DB 서비스(서버군), DB Server(개별 서버), 기본 DB 명(첫 데이터베이스). 접속 주소는 넷째 이름이 아니라 플랫폼이 만들어 주는 값이다
- DB 서비스가 서버들의 그룹이라는 점 — `Stand Alone`·`Master`·`Standby Master`·`Slave`·`Recovery` 다섯 역할이 그 안에 들어가며, DB Server 이름에 `-001-xxxx`가 자동으로 붙는 것도 그룹 안에서 서버를 식별하기 때문이다
- Subnet을 하나 선택하고 생성한 뒤에는 이전할 수 없다는 점, 공인 도메인이 Public Subnet에 배치한 서버에서만 신청된다는 점, 선택 목록에 `용도`가 `일반`인 Subnet만 조회되어 NAT Gateway·Load Balancer와 반대로 전용 유형이 배제된다는 점
- `고가용성 지원`이 화면을 바꾼다는 점 — 사용하면 `Multi Zone`이 활성화되고 Subnet 선택이 Master와 Standby Master 둘로 나뉜다. 생성 이후에 고가용성으로 변경할 수 있다
- 접속 포트가 `3306` 또는 `10000`~`20000`이라는 점 — 기본 포트를 선택하면 접속할 때 포트를 명시하지 않아도 되고, 범위 안의 다른 값을 선택하면 접속 문자열과 클라이언트 옵션에 매번 지정해야 한다
- 접속 주소가 `{db-xxxxxx}.vpc-cdb.ntruss.com`이고 Private Sub 도메인을 지정하면 그 값이 사이에 들어간다는 점 — 지정하든 않든 플랫폼이 `db-xxxxxx`를 앞에 붙여 고유성을 보장하므로 이름에 유일 값을 덧붙일 필요가 없다. Bucket이 이름 자체로 주소가 되어 `{uniq}`를 요구했던 것과 대조된다
- 관리자 계정의 권한이 전체 범위에 데이터를 다루는 것을 포함하지 않는다는 점 — `*.*`에는 `PROCESS`·`SHOW DATABASES`·`REPLICATION`·`CREATE USER`만 있고 데이터를 다룰 수 있는 곳은 생성 화면에서 지정한 기본 DB 하나뿐이며, `CREATE`가 없어 데이터베이스를 만들 수 없다
- 데이터베이스를 콘솔 `Database 관리`로 추가하고 사용자와 권한은 SQL로 부여한다는 점 — 이 경계가 관리형이 어디까지 담당하는지를 보여주며, 거부될 때의 `ERROR 1044 (42000): Access denied`에 계정이 `dbadmin@'10.0.%'`로 표시되어 HOST(IP)도 계정의 일부라는 것이 함께 드러난다
- 계정 목록에 `radmin`과 `agent`가 있다는 점 — `Host`가 `localhost`·`127.0.0.1`이라 VPC 안에서 접속할 수 없으며, 관리형이 서버 안에 자기 계정을 두고 운영을 수행한다는 것이 목록에 남아 있다
- 생성 화면의 `DB Data Load`가 신규 생성과 Object Storage 백업 파일 둘이라는 점 — 어느 쪽이든 기본 DB 명을 입력해야 하므로 사용하지 않을 데이터베이스가 하나 만들어진다
- 콘솔 `DB User 관리`가 권한을 모든 데이터베이스에 적용한다는 점 — 특정 데이터베이스로 좁히려면 SQL `GRANT`를 사용해야 한다
- `USER_ID`가 특정 DB 전용 사용자가 아니라 관리자 계정이라는 점 — `root`는 제공되지 않고 이 계정이 그 자리를 대신한다
- 생성 화면에서 지정하는 데이터베이스와 계정은 처음 만들어지는 것일 뿐이라는 점 — 이후 콘솔이나 SQL로 추가하며 DB는 최대 1,000개까지 가능하다. 다만 `sys.ncp_` 프로시저가 별도로 제공되어 일반 SQL이 제한될 수 있다
- 접근 통제가 두 계층이고 순서가 통제 방식을 정한다는 점 — ACG가 앞에서 걸러 통과한 트래픽만 계정 조건에 도달하므로 출발지 통제를 ACG에 모은다
- 자동 생성되는 ACG가 자기 자신을 접근 소스로 갖는다는 점 — `cloud-mysql-`로 시작하는 이름이고 규칙이 비어 있지 않으며, 그 ACG가 적용된 대상끼리만 통신한다. 플랫폼이 만든 자원이지만 규칙은 편집할 수 있으므로 접근할 대상의 ACG를 소스로 추가하여 경로를 연다
- 소스를 대역이 아니라 ACG로 지정하는 이유 — 접근하는 쪽이 서버라 가리킬 ACG가 있기 때문이며, ACG가 없는 Load Balancer에 대역을 지정했던 「Application Load Balancer 구성」과 같은 기준이 반대 결론을 낸다
- Auto Scaling Group이 ACG를 하나만 지정한다는 제약이 방식을 정한다는 점 — 대상 Network Interface에 ACG를 추가하는 방법은 그룹이 생성하는 서버에 쓸 수 없다

## Examples

- `lab17` → 「VPC와 Subnet」에서 예약한 `10.0.103.0/24`에 데이터베이스 전용 Subnet을 생성하고 그 위에 `Stand Alone`으로 DB Server를 만든다
- Private Subnet의 서버에서 관리자 계정으로 접속하여 권한을 조회하고 `CREATE DATABASE`가 거부되는 것을 확인한 뒤, 콘솔로 데이터베이스를 추가하고 SQL로 그 데이터베이스에만 권한을 갖는 계정을 만든다 — Bastion은 경유에만 사용한다
- 데이터베이스와 테이블은 반납하지 않는다. 「백업과 복원」이 복원 대상으로 사용한다
