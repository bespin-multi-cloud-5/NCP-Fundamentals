# 07 Cloud DB for MySQL / 04 백업과 복원

관리형 데이터베이스의 백업 구성과 복원 절차를 다룬다. 복원이 만들어 내는 결과물이 원본을 대체하지 않는다는 점, 그리고 「Cloud DB for MySQL 생성과 연결」에서 서버를 한 대만 두기로 한 결정이 복구 수단의 범위를 함께 정한다는 점이 중심이다.

## What you will learn

- 자동 백업이 생성 시점에 함께 설정되고 이후 별도의 조작 없이 수행된다는 점 — 하루 한 번, 보존 기간은 최대 30일이며 시각을 지정하면 그 시각부터 15분 안에 시작한다
- 백업 파일로 되돌릴 수 있는 지점이 백업이 수행된 시각뿐이라는 점 — 그 이후의 변경을 채우는 것은 바이너리 로그이고 복구 구간은 `binlog_expire_logs_seconds`가 결정한다
- 복원이 기존 데이터베이스를 덮어쓰지 않는다는 점 — `Recovery` 타입의 신규 서버가 생성되고 원본은 운영 상태를 유지하므로, 복원 시각을 잘못 지정해도 다시 수행하면 된다
- 복원이 두 단계로 나뉜다는 점 — 데이터를 복구한 서버를 생성한 뒤 그 서버를 기반으로 새 DB 서비스를 구성해야 서비스에 사용할 수 있다
- 시점 복원이 분 단위까지 지정된다는 점 — 마지막 백업 시점이 아니라 삭제 직전으로 복구할 수 있고, 백업 주기가 하루 한 번이므로 두 방식의 차이는 최대 24시간 분량이다
- `Stand Alone`이 시점 복원과 수동 백업을 사용할 수 없다는 점 — 자동 백업과 백업으로 복원하는 기능은 두 구성 모두 지원한다
- 가용성 구성이 복구 수단의 범위까지 결정한다는 점 — 서버 개수의 결정이 장애 대응뿐 아니라 백업 기능에도 적용되며, `Stand Alone`과 고가용성 사이의 전환은 데이터를 유지한 채 수행된다

## Examples

- `lab18` → 「Cloud DB for MySQL 생성과 연결」이 `Stand Alone`으로 생성한 데이터베이스라 시점 복원이 제한되는 지점에서 시작한다
- 고가용성으로 전환하여 시점 복원과 수동 백업이 함께 열리는 것을 확인한다 — 전환은 `Recovery`, `Slave`, `Master` 순서로 진행되고 데이터는 유지된다
- 데이터를 삭제하고 삭제 직전 시각으로 복원한 뒤, 복구 서버와 원본을 나란히 조회하여 원본이 덮어써지지 않은 것을 확인한다
- 접속은 Bastion에서 수행한다. `labuser`의 접근 허용 주소가 `10.0.%`라 앞 실습에서 반납한 서버를 다시 만들지 않아도 된다
