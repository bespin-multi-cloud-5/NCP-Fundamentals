# 06 Object Storage / 03 공개와 자격증명

앞 섹션에서 파일 하나를 공개하여 브라우저로 확인했다. 버킷에도 같은 이름의 설정이 있는데 둘이 어떻게 다른지, 그리고 콘솔에 로그인하지 않는 애플리케이션이 접근할 때는 무엇이 필요한지를 다룬다.

## What you will learn

- Object Storage에 도달하는 방식이 둘이라는 점 — 공개는 아무나 조회할 수 있는지를, 자격증명은 요청하는 쪽이 누구인지를 판별하며 서로 독립이다
- 공개가 버킷과 파일에 각각 적용된다는 점 — 버킷을 공개해도 그 안의 파일이 함께 공개되지 않고 목록에 이름이 표시될 뿐이다
- 자격증명이 둘로 나뉜다는 점 — 키를 저장하는 방식(인증키)과 저장하지 않는 방식(서버 역할)
- 인증키가 Sub Account에 부여된다는 점 — 그 계정으로 콘솔에서 수행할 수 있는 작업이 곧 그 키로 API에서 수행할 수 있는 작업이다
- 위치가 방식을 결정한다는 점 — 서버 역할은 NCP VPC 안의 서버에만 부여되므로 개발자 PC나 외부 빌드 서버는 인증키를 사용한다
- 인증키는 제거할 대상이 아니라 필요한 곳에만 두고 관리할 대상이라는 점
- 작업 계정의 `NCP_INFRA_MANAGER` 때문에 키 하나가 결제를 제외한 계정 전부에 해당한다는 점
- Secret Key를 언제든 다시 확인할 수 있고 개수 제한도 없다는 점 — 편리한 만큼 관리가 사람의 몫이 된다
- 키를 교체하는 절차 — 사용하는 곳을 찾는 것이 가장 어렵고 그동안 이전 키는 유효하다
- 서버 역할이 그 부담을 제거하는 방식 — 저장할 키가 없고 만료되며 범위를 좁힐 수 있다
- 관리를 잘 수행하는 것보다 관리 대상 자체를 줄이는 편이 확실하다는 점
- 버킷의 `접근 제어`가 「요청이 어디에서 왔는가」라는 세 번째 축이라는 점 — 사설 도메인과 등록된 서버 두 조건을 함께 만족해야 접근되므로 브라우저로 조회하는 구성에는 사용할 수 없다
- 다른 계정에 ACL을 부여하는 것은 API에만 있고 콘솔에는 없다는 점

## Examples

- `lab16` → 버킷을 공개하여 목록은 표시되는데 파일은 조회되지 않는 것을 확인하고, 인증키를 발급하여 같은 파일을 조회한다. 공개 설정은 변경하지 않으므로 달라지는 것은 요청하는 쪽의 증명 여부뿐이다
- S3 호환이라 `aws` CLI가 그대로 연결된다 — `06.01`에서 문서로만 확인한 것을 직접 검증한다
- NCP 밖의 PC에서 인증키만으로 파일을 삭제하고 그 결과가 콘솔에 반영되는 것, 그리고 그 키가 계정의 버킷 전부를 조회하는 것을 확인한다
- 키를 발급하지 않는 방식(Server Role)은 다음 섹션에서 Gallery에 적용한다
